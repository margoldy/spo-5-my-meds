# Шифрование медицинских данных

## Выбранная схема

На телефоне создаётся случайный ключ `DEK`, которым шифруются медицинские данные. Пользователь задаёт пароль шифрования. Из пароля только на телефоне через `Argon2id` получается ключ `KEK`.

Телефон шифрует `DEK` ключом `KEK` через `AES-256-GCM`. Сервер хранит медицинские данные и `DEK` только в зашифрованном виде.

Таким образом, пароль не шифрует медицинские данные напрямую: он защищает ключ, которым они зашифрованы. Такой подход называется конвертным клиентским шифрованием.

## Использование

На новом телефоне пользователь один раз вводит пароль. Телефон получает с сервера зашифрованный `DEK`, открывает его и сохраняет локальную копию под защитой `Android Keystore`. 

При шифровании `DEK` алгоритм `AES-256-GCM` создаёт проверочную метку. Во время расшифрования он автоматически проверяет эту метку: из правильного пароля получается правильный `KEK`, и проверка проходит; из неправильного пароля получается другой `KEK`, поэтому AES-GCM возвращает ошибку. При смене пароля заново шифруется только `DEK`, а не все медицинские данные.

Сервер не знает пароль и открытый `DEK`, поэтому не может восстановить медицинские данные при утрате пароля. Вход по email подтверждает аккаунт, но не заменяет пароль шифрования.

## Что хранит backend

`User.encrypted_dek` содержит salt Argon2id, nonce AES-GCM, зашифрованный `DEK` и tag в одной строке. `Course.encrypted_data`, `Schedule.encrypted_data` и `Intake.encrypted_data` содержат nonce, ciphertext и tag также в одной строке. Формат строки задаёт мобильное приложение, сервер её не разбирает.

Открытыми остаются идентификаторы, связи, даты курса, время и дни расписания, время фактического приёма и состояние курса. Они нужны серверу для проверки владельца, выборок и построения календаря. Название лекарства, заметки и дозы открытым текстом не передаются.

Зашифрованный `DEK` передаётся через `GET` и `PUT /api/v1/users/me/encryption-key`. Все медицинские endpoints принимают и возвращают `encrypted_data`.

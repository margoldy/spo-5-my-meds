# Речь к презентации «Моя аптечка»

## Слайд 1. Моя аптечка

Наш проект называется «Моя аптечка». Это приложение для ведения курсов лекарств, расписания и истории приёмов. На текущем этапе уже работают frontend на Vue 3 и backend на FastAPI. Приложение позволяет не просто сохранить название лекарства, а описать весь курс: период, дозировку, несколько времён приёма и дни недели. Отдельное внимание мы уделили защите медицинских данных и сделали клиентское шифрование.

## Слайд 2. Проблема

Когда человек принимает несколько лекарств, обычного списка уже недостаточно. У каждого препарата может быть своё время, дозировка и длительность курса. В течение дня легко забыть, что уже принято, а что ещё нет. При этом расписание, инструкция и история часто хранятся в разных местах. Из-за этого возникает риск пропустить приём или принять лекарство повторно. Приложение собирает эти данные в одном интерфейсе и показывает актуальный план на выбранный день.

## Слайд 3. Что уже работает

Сейчас реализованы основные пользовательские экраны. В календаре видны приёмы на конкретную дату и их состояние. В разделе курсов отображаются активные и завершённые назначения. В справочнике есть поиск и фильтры по категории и форме препарата. Интерфейс рассчитан на ширину телефона, но его можно открыть и на компьютере. В таком случае приложение остаётся по центру, а свободное место по бокам заполняется нейтральным фоном.

Справочник уже не пустой. В него добавлены сто записей из открытых данных Государственного реестра лекарственных средств Минздрава России. Это начальная выборка, которую в дальнейшем можно расширять.

## Слайд 4. Курсы и расписание

Основная сущность для пользователя — курс. В нём хранится выбранный препарат или собственное название, дата начала и необязательная дата окончания. У одного курса может быть несколько записей расписания. Например, один препарат можно принимать в восемь утра, в три часа дня и в девять вечера.

Для каждого времени отдельно указываются дозировка, единица измерения и дни недели. Поэтому утренний и вечерний приём не обязаны быть одинаковыми. Новое время можно добавить прямо в форме создания или редактирования курса. Если расписание не добавлено, курс считается приёмом по необходимости и не создаёт события в календаре заранее.

## Слайд 5. Приёмы и история

Календарь показывает плановые приёмы, рассчитанные по курсам и расписанию. При подтверждении пользователь может изменить фактическое время и дозу, потому что реальный приём не всегда полностью совпадает с планом. После сохранения запись появляется в истории.

Внеплановый приём можно создать двумя способами. Первый вариант — выбрать лекарство из существующего курса. Второй — записать отдельный приём без курса и вручную указать название и дозировку. В историю копируются фактическое название и доза. Поэтому последующее редактирование курса не меняет старые записи и не искажает историю.

## Слайд 6. Справочник и роли

Справочник общий для всех пользователей. Гость может просматривать активные препараты без регистрации. Обычный пользователь выбирает препарат из справочника при создании курса, но не может изменять сами справочные записи. Администратор может добавлять, редактировать и скрывать препараты.

При этом роль администратора не даёт доступ к медицинским данным пользователей. Курсы и приёмы запрашиваются только вместе с идентификатором владельца, а чувствительные поля дополнительно хранятся в зашифрованном виде. Таким образом, управление справочником отделено от личных данных.

## Слайд 7. Структура приложения

Приложение разделено на три основные части. Frontend на Vue 3 отвечает за экраны, локальные настройки, работу с токенами и шифрование через Web Crypto. Он обращается к backend по REST API. FastAPI проверяет данные запросов, текущего пользователя, права доступа и роль. Для авторизации используются JWT.

PostgreSQL хранит пользователей, общий справочник и данные приложения. Медицинские поля курсов и приёмов попадают в базу уже зашифрованными. Для работы с таблицами используется SQLAlchemy. Отдельно подключён SMTP-сервис, через который отправляется одноразовый код входа на электронную почту.

## Слайд 8. Шифрование медицинских данных

Шифрование происходит на устройстве пользователя до отправки данных на сервер. Приложение создаёт случайный ключ для медицинских записей. Пользовательский пароль защищает этот ключ, но не отправляется на backend и не хранится там.

Перед использованием пароль усиливается алгоритмом Argon2id. Медицинские поля шифруются алгоритмом AES-256-GCM. Он одновременно скрывает содержимое и проверяет, что зашифрованные данные не изменили. Если пароль введён неверно, приложение не сможет открыть сохранённый ключ и расшифровать записи.

Сервер хранит только закрытый служебный ключ и зашифрованные медицинские поля. Открытыми остаются идентификаторы, даты и время, потому что без них backend не сможет построить календарь и проверить владельца записи. Названия, дозировки и заметки открытым текстом не передаются.

## Слайд 9. Авторизация и контроль доступа

Вход выполняется по электронной почте. Пользователь получает шестизначный одноразовый код. Код действует пять минут, повторно запросить его можно через минуту, а после пяти неверных попыток он блокируется. После успешной проверки backend выдаёт два токена. Access-токен используется для обычных запросов и действует тридцать минут. Refresh-токен действует тридцать дней и позволяет обновить сеанс без повторного ввода кода.

Одних токенов недостаточно, поэтому каждый запрос к личным данным дополнительно проверяет владельца. Если идентификатор курса или приёма передан в URL, backend всё равно ищет запись вместе с `user_id` текущего пользователя. Роль администратора применяется только к операциям со справочником и не отменяет эту изоляцию.

## Слайд 10. Текущее состояние

Сейчас frontend обращается к настоящему API, автоматически обновляет access-токен и показывает данные из backend. Работают курсы, несколько расписаний внутри курса, плановые и внеплановые приёмы, история, поиск по справочнику и клиентское шифрование. Сборка frontend проходит успешно, для backend подготовлено одиннадцать автоматических тестов.

Есть и ограничения текущего прототипа. Браузерные уведомления работают только пока открыта страница. Для локального хранения ключевой информации используется IndexedDB, тогда как в нативном приложении нужно защищённое хранилище операционной системы. Схема учебной базы пока создаётся через SQLAlchemy без миграций, поэтому при изменении моделей базу приходится пересоздавать. Публичное развёртывание также ещё не выполнено.

## Слайд 11. Будущее: мобильное приложение

Первое крупное направление развития — мобильная версия для Android. Текущий интерфейс и API уже можно использовать как основу, поэтому основная новая работа связана с возможностями самой операционной системы.

Системные уведомления смогут приходить по расписанию, даже когда пользователь закрыл приложение. Локальная часть шифрования будет храниться в Android Keystore, а биометрия сможет открывать уже настроенное хранилище на конкретном устройстве. При входе на новом телефоне пользователь снова вводит пароль шифрования, после чего приложение получает зашифрованные данные и открывает их локально.

## Слайд 12. Будущее: публикация

Второе направление — постоянная публикация backend. Frontend можно разместить на GitHub Pages, но ему нужен стабильный публичный адрес API с HTTPS. Для этого подойдёт сервер или хостинг, который автоматически запускает приложение после перезагрузки и проверяет его состояние.

CORS будет разрешать обращения только с опубликованного адреса frontend и с локального адреса разработки. Почтовый пароль, JWT-секрет и параметры подключения к базе должны храниться в переменных окружения, а не в репозитории. PostgreSQL не должна принимать подключения из интернета. К ней обращается только backend. Для базы также нужны резервные копии и отдельный пользователь с ограниченными правами.

## Слайд 13. Дальнейшее развитие

После публикации нужно повысить устойчивость проекта. Изменения структуры базы будут оформляться миграциями, а основные пользовательские сценарии будут проверяться интеграционными тестами. Журнал ошибок и мониторинг помогут заметить сбой до того, как о нём сообщит пользователь.

Справочник можно регулярно обновлять по данным ГРЛС и дополнить ссылками на официальные инструкции. Следующий продуктовый этап включает экспорт истории для врача, отдельные профили для близких и статистику пропусков. Эти функции не входят в текущую реализацию, но существующая модель курсов, расписаний и фактических приёмов уже позволяет развивать приложение в этом направлении.
